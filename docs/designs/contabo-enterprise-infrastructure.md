## 1. Problem Statement
Digital agencies, software houses, and enterprise development teams waste 10–20 hours per client setting up and maintaining dedicated PostgreSQL databases, Linux VPS instances, SSL certificates, backup cron jobs, and OS security patches. When managing 10–30 client CMS instances, manual sysadmin work creates severe operational bottlenecks, high risk of unmonitored backup failures, and weekend downtime emergencies.

---

## 2. Demand Evidence & Realities
- **Current Bottleneck**: Pre-product / early validation phase targeting software houses and tech agencies.
- **Pain Point**: Dev teams are stuck writing custom bash scripts or manually configuring Contabo/DigitalOcean servers.
- **Enterprise Friction**: High-tier enterprise clients reject shared multi-tenant databases due to compliance, privacy, and noisy-neighbor performance concerns.
- **Willingness to Pay**: Agencies are eager to replace $300+/month managed cloud services (or 15 hours of senior engineer sysadmin time) with an automated, transparently priced dedicated infrastructure solution.

---

## 3. Status Quo
- **Manual Self-Hosting**: Spinning up generic VPS instances, manually installing Docker/PostgreSQL, configuring `pg_hba.conf`, and setting up rudimentary local cron backups.
- **Fragility**: Lack of cloud-level firewalls, lack of automated block-level snapshots, and zero automated health checking or self-healing.
- **Cost vs Ops Trade-off**: Strapi Cloud / Contentful cost $300–$1,000+/month without data sovereignty in target regions (e.g. Singapore / Indonesia), while raw Contabo VPS costs only €5.50/month but requires heavy DevOps labor.

---

## 4. Target User & Narrowest Wedge
- **Target Persona**: Tech Lead / CTO at Digital Agencies & Software Houses managing 10–30 client projects.
- **Career Stake**:
  - *Promotion/Win*: Delivering client headless CMS backends in 2 hours instead of 2 weeks with zero recurring sysadmin overhead and earning a healthy managed hosting markup.
  - *Risk/Nightmare*: Client database crashes on a weekend, local backups turn out corrupted, or security breach via unpatched ports.
- **Narrowest Wedge (Day-1 Deliverable)**:
  - Automated 1-Click Provisioning of hardened PostgreSQL 16 on Contabo Cloud VPS/VDS.
  - Hardware-level protection using **Contabo Cloud Firewall API** (`/v1/firewalls`).
  - Dual-layer backup: Daily logical `pg_dump` encrypted to Cloudflare R2 + Weekly block-level **Contabo Snapshots** (`/v1/compute/instances/{id}/snapshots`).

---

## 5. Constraints
1. **Contabo API Authentication**: OAuth2 Password Grant flow (`https://auth.contabo.com/auth/realms/contabo/protocol/openid-connect/token`) with token expiration caching.
2. **Boot Latency**: Contabo VPS creation + cloud-init execution takes ~2 to 4 minutes. Provisioning must be strictly asynchronous with state-machine progression (`REQUESTED -> CREATING_VPS -> BOOTING -> PROVISIONING_DB -> HEALTHCHECK -> ACTIVE`).
3. **Database Security**: Postgres port `5432` must NEVER be exposed openly to the public internet. It must be locked down via Contabo Cloud Firewall and `ufw` to whitelist only SaCMS backend server IP addresses.

---

## 6. Agreed Premises
1. **Architectural Wedge**: From Contabo's 29,425-line OpenAPI spec (`openapi.json`), SaCMS focuses strictly on 4 essential pillars:
   - Compute Instance Lifecycle (`/v1/compute/instances`)
   - Cloud Firewall Automation (`/v1/firewalls`)
   - Cloud-Init DB Bootstrapping (PostgreSQL 16, pg_hba, tuning, Node Exporter)
   - Snapshot Disaster Recovery (`/v1/compute/instances/{instanceId}/snapshots`)
2. **Zero-Ops Abstraction**: Tenants and agencies interact only with the SaCMS dashboard. The underlying VPS credentials, SSH keys, and cloud-init routines are managed autonomously by SaCMS.

---

## 7. Approaches Considered

### Approach A: Minimal Wedge (Direct Async Provisioner + Cloud-Init)
- *Summary*: Basic route handler triggers `POST /v1/compute/instances` with cloud-init script. Status checked via simple polling.
- *Effort*: S (human: ~2 days / CC: ~30 min) | *Risk*: Low
- *Ruling*: **Ruled out** — Relies solely on OS-level `ufw` and lacks cloud firewall API enforcement and 1-click snapshot rollback.

### Approach B: Resilient Enterprise Orchestrator (State-Machine + Contabo Cloud Firewall + Auto-Snapshot + R2 Backup)
- *Summary*: Robust event-driven state machine managing VPS creation, cloud firewall attachment, cloud-init DB bootstrap, automated connection verification, dual backup strategy (R2 logical + Contabo block snapshot), and automated recovery.
- *Effort*: M (human: ~1 week / CC: ~1.5 hours) | *Risk*: Low-Med
- *Ruling*: **CHOSEN (Recommended)** — Delivers true enterprise SLA, maximum security, and hands-off reliability for tech leads.

### Approach C: Hybrid BYOK Control Plane (Client brings own Contabo API key)
- *Summary*: SaCMS acts as a pure control plane (like Laravel Forge) where agencies input their own Contabo API credentials.
- *Effort*: L (human: ~2 weeks / CC: ~2.5 hours) | *Risk*: Med
- *Ruling*: **Ruled out** — Adds significant onboarding friction for agencies that prefer an all-in-one managed billing experience.

## 8. Recommended Approach Architecture (Approach B)

### Component Flow
```text
[SaCMS Dashboard / Tenant Checkout]
              │
              ▼
   (1) Trigger Provisioning
              │
              ▼
[src/lib/infrastructure/provisioner.ts]
  ├── (Step A) Request Contabo Cloud Firewall: Create/Attach SaCMS Whitelist Rule
  ├── (Step B) Create Instance via POST /v1/compute/instances with cloud-init
  ├── (Step C) Update DB state: InfrastructureServer.status = "PROVISIONING"
  │
  ▼
[Contabo Cloud (openapi.json)] ──(Boot ~2-3 mins)──► [Dedicated VPS]
                                                     ├── PostgreSQL 16 (Tuned)
                                                     ├── SSL / TLS Certificates
                                                     ├── Node Exporter (Metrics)
                                                     └── R2 Backup Daemon
  │
  ▼
[Async Healthcheck Worker / Cron]
  ├── (Step D) Poll GET /v1/compute/instances/{instanceId} until status == "ok"
  ├── (Step E) Probe PostgreSQL port & run test query (`SELECT 1;`)
  ├── (Step F) Trigger initial Contabo Snapshot: POST /v1/compute/instances/{id}/snapshots
  └── (Step G) Mark Server "ACTIVE" -> Store encrypted connection string in Tenant DB Config
```

### Contabo API Endpoints Mapped from `openapi.json`
| Purpose | Contabo Endpoint | Method |
|---|---|---|
| OAuth2 Auth | `/auth/realms/contabo/protocol/openid-connect/token` | POST |
| Create VPS | `/v1/compute/instances` | POST |
| Get Status & IP | `/v1/compute/instances/{instanceId}` | GET |
| Lifecycle (Restart/Stop) | `/v1/compute/instances/{instanceId}/actions/{restart\|stop}` | POST |
| Cloud Firewall | `/v1/firewalls`, `/v1/firewalls/{id}/instances/{instanceId}` | POST |
| Snapshot Create | `/v1/compute/instances/{instanceId}/snapshots` | POST |
| Snapshot Rollback | `/v1/compute/instances/{instanceId}/snapshots/{snapshotId}/rollback` | POST |
| Server Cancellation | `/v1/compute/instances/{instanceId}/cancel` | POST |

## 9. Open Questions & Edge Cases
1. **Contabo Region Capacity**: How to handle temporary out-of-stock events in specific regions (e.g., Singapore `SIN`)?
   - *Resolution*: Implement automatic fallback to secondary region or queue request with clear user alert.
2. **Snapshot Retention**: Contabo limits snapshot count based on plan.
   - *Resolution*: Maintain 1 primary weekly golden snapshot on Contabo, supplemented by 30-day versioned daily backups on Cloudflare R2.

---

## 10. Success Criteria
1. Fully automated dedicated database provisioning completed in `< 4 minutes` from tenant checkout.
2. Zero public exposure of PostgreSQL port 5432 (100% protected by Contabo Cloud Firewall).
3. 1-Click rollback from dashboard using Contabo Snapshot API in case of accidental data corruption.
4. Seamless integration with `getTenantDb(tenantId)` dynamic connection routing in SaCMS.

## 13. NOT in Scope
- **Contabo Domain Registrar & Transfers** (`/v1/domains`): SaCMS manages subdomains via existing DNS providers (Cloudflare), not registrar reselling.
- **Custom ISO / QCOW2 Image Upload** (`/v1/compute/images`): SaCMS standardizes on official Ubuntu 24.04 LTS images with cloud-init bootstrap.
- **Floating VIP Management** (`/v1/vips`): Deferred to future multi-node high-availability enterprise clustering.
- **Contabo Private Networks / Cross-DC VPC**: Deferred to multi-region disaster recovery tier.
