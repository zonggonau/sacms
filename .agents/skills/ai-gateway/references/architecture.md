# AI Site agent: setup, model, tools, quota

## Gateway setup

- `src/lib/ai.ts`'s `resolveGatewayModel(overrideModel?)` is the single chokepoint for every AI feature in SaCMS — it resolves the admin-configured Gateway API key + base URL (`getResolvedAiConfig()` in `src/lib/settings.ts`) and returns `{ model, modelId }` via `@ai-sdk/gateway`'s `createGateway()`. Call it instead of constructing a Gateway client yourself.
- Credential resolution is DB-first: `src/lib/settings.ts`'s `applyEnvFallbacks()` only falls back to `.env` (`AI_GATEWAY_API_KEY`, `VERCEL_ACCESS_TOKEN`, etc.) when the Admin Settings DB field is *empty* — a non-empty but stale DB value always wins, even over a correct `.env` value. If a credential that looks right in `.env` still fails, check Admin → Settings → Mesin AI for a stale override before assuming the credential itself is bad. This bit twice in one session (the Vercel token, then the Gateway key).
- `enforceAiQuota`/`refundAiQuota`/`recordAiUsage` (also `src/lib/ai.ts`) are the shared credit-ledger primitives every AI feature reserves/refunds/records through. `enforceAiQuota` already reserves credits internally for the `userId` path — never call `reserveUserAiCredits` again on top of it, that double-charges.
- **`enforceAiQuota` signals "out of credits" by throwing a plain `Error` with `.status = 429`** and an already user-safe, pre-written message ("AI credits depleted... Please top up..."). `handleRouteError` (`src/lib/api/route-helpers.ts`) special-cases this exact shape and returns it as a real `rate_limited` 429 instead of its usual masked "Something went wrong" 500 — that fix came from a live bug: AI Site's messages route and the AI Schema Generator's plan-schema route both called `enforceAiQuota` with no local catch, so a depleted account saw a generic crash instead of "top up your credits." **Never catch a `enforceAiQuota` error and quietly substitute fallback/free behavior** — the AI Schema Generator did exactly that (any error, including 429, triggered a free canned-schema fallback with `usedFallback: true`), which both hid the real cause behind a misleading "AI Gateway tidak merespons" message and let a depleted account keep generating unlimited free schemas. The fix was to re-throw on `error.status === 429` before the fallback logic runs, so only genuine infra failures (Gateway not configured, timeout) fall back — a real quota boundary never should.
- This Gateway account denies Claude models on its current tier ("Free tier users do not have access to this model" — confirmed live for both `anthropic/claude-sonnet-5.5` and `-4.5`). `openai/gpt-5-mini` and `google/gemini-2.5-flash` both work. Check access cheaply before switching any default: `generateText({ model: 'openai/gpt-5-mini', prompt: 'Reply with OK', maxOutputTokens: 16 })`.

## The AI Site builder agent

**One project per workspace, one chat per project** — it's the single website being developed, not one of many (enforced with 409s in `src/app/api/tenant/[tenant]/ai-site/projects/route.ts` and `.../projects/[projectId]/chats/route.ts`). The landing page (`src/app/(workspace)/dashboard/[tenant]/developer/aisite/page.tsx`) is a v0.dev-style single prompt box when no project exists yet — one input, one "build it" action, no project-name field, no settings to configure first; once a project exists, it redirects straight into the chat workspace.

- `src/app/api/tenant/[tenant]/ai-site/chats/[chatId]/messages/route.ts` is the single generation endpoint, wrapped in `withStaffAuth`. It resolves `access` from the session itself — there is no separate `authorizeChatRequest`/bearer-token layer like a standalone multi-tenant app would need.
- The client sends only its newest message (`prepareSendMessagesRequest` in `src/components/dashboard/ai-site/chat-conversation.tsx`). The route loads history from the tenant's own Prisma DB (`src/lib/ai-site/chats.ts`) and rebuilds the user message from its text, so a client can't inject tool results or assistant turns. Keep it that way.
- Model: **user-picked per chat from the Gateway's full live catalog, not the platform default — and changeable mid-conversation**. This replaced an earlier curated 3-model shortlist (explicit user request: "gunakan seluruh model yang ada, user bebas memilih model AI"). `fetchGatewayLanguageModels()` (`src/lib/ai.ts`) calls the Gateway SDK's own `gateway.getAvailableModels()` and filters to `modelType === "language"` (the same catalog also lists image/video/embedding/speech/etc. models, which can't serve a chat/tool-calling feature) — served through `GET .../ai-site/models` (cached in-memory 10 min; `withStaffAuth`, `minRole: "editor"`). `src/lib/ai-site/models.ts` now holds **only** client-safe constants (`DEFAULT_AI_SITE_MODEL`, `FALLBACK_AI_SITE_MODEL_OPTIONS` for before the live list loads or if the fetch fails, `isAllowedAiSiteModel` — a loose `provider/model-id` shape guard, not a semantic allowlist) — no server-only import, because `chat-workspace.tsx` is a client component that needs `DEFAULT_AI_SITE_MODEL`, and the live-fetch logic (which reaches `database.ts`/`license.ts` through `ai.ts`) breaks the client/server bundle boundary if it's in the same file (confirmed live via a failed build: "Client Component Browser" import trace through `ai-site/models.ts` → `ai.ts` → `database.ts` → `license.ts`). Client-side, `useAiSiteModels()` (`src/hooks/use-ai-site-models.ts`) fetches the live list and starts with the same fallback. `AiSiteLanding` (`src/components/dashboard/ai-site/ai-site-landing.tsx`) shows this dropdown at the moment the chat is created; the choice is stored on `AiSiteChat.model` (nullable — falls back to `DEFAULT_AI_SITE_MODEL` for older chats or an unset pick), validated server-side (`POST .../chats`) only against the loose shape guard now, not a hardcoded list — an invalid-but-well-formed id still fails clearly at the actual Gateway call, which is an acceptable outcome for a value only a direct API call (not the dropdown) could produce. The *same* dropdown also appears in `chat-conversation.tsx`'s toolbar for an existing chat — changing it calls `PATCH .../ai-site/chats/[chatId]` (validated the same way, via `updateChatModel` in `src/lib/ai-site/chats.ts`). The messages route resolves `chat.model || DEFAULT_AI_SITE_MODEL` fresh on every turn, so a change takes effect starting the *next* turn, never retroactively for one already streaming. `AI_SITE_FALLBACK_MODELS` (`src/lib/ai-site/quota.ts`) is a separate, fixed Gateway-level fallback tried if whichever primary model the chat picked is ever unavailable — independent of the user's choice. A 40-step tool-calling loop needs far more reliable function calling than a one-shot generation; that's why this overrides the platform-wide admin default at all. Known, accepted trade-off of opening the full catalog: a model some tenant picks may 403/429 on this Gateway account's tier, or may simply be worse at reliable function-calling than the old curated picks — that's now the user's informed choice, not something pre-filtered away.
- Credits are shown, not just enforced: `AiCreditsBadge` (`src/components/dashboard/ai-site/ai-credits-badge.tsx`) is a small client component hitting the existing, account-wide `GET /api/ai/account-credits` (also backs the billing page) — used on `AiSiteLanding` and in the chat toolbar (`refreshKey` bumped after every turn via `onFinish`, so the balance updates without a page reload). Added after a live bug where a depleted account's first sign anything was wrong was a mysterious failed generation — see the 429-handling note above.
- `streamText` runs with `system: aiSiteSystemPrompt(...)` (`src/lib/ai-site/prompt.ts`), `messages: await convertToModelMessages(history, { tools, ignoreIncompleteToolCalls: true })`, the tools below, `stopWhen: stepCountIs(40)`, and `repairToolCall` (see below).
- Credits are a **fixed cost per turn** (`AI_SITE_TURN_COST = 50`), not metered by tokens — product decision, not a placeholder. `reserveAiSiteTurn` before `streamText`, `refundAiSiteTurn` only if setup fails before streaming starts (a turn that starts streaming and then errors is not refunded — real Gateway spend already happened). Verified by re-reading the route after every later change this session: one reserve call, two refund call sites, both strictly before `streamStarted = true`. Never add a third refund path without checking it's still pre-stream.
- `result.toUIMessageStreamResponse({ originalMessages, generateMessageId, onFinish })` streams to `useChat` and saves the response message + records usage in `onFinish`.

### Tool-call repair

Some models occasionally hallucinate a garbled tool name (seen live: `WritefilesFiles` instead of `writeFiles`), which the AI SDK rejects outright (`NoSuchToolError`) and kills the whole turn. `src/lib/ai-site/repair-tool-call.ts`'s `repairAiSiteToolCall` fuzzy-matches (Levenshtein distance, relative threshold) the hallucinated name against the real tool list and rewrites the call in place; wired via `streamText`'s `repairToolCall` option. Keep this wired for any new tool set added to the agent — it's cheap insurance, not a substitute for picking a tool-reliable model.

**A different failure mode fuzzy-matching can't fix**: seen live with a Gemini model — `AI_NoSuchToolError: Model tried to call unavailable tool 'google:python_interpreter'`, with the "call" actually being generated Python source calling `default_api.CmsCreateContentTypeFields(...)`. This isn't a garbled name close to a real one (Levenshtein matching correctly declines to "fix" it into some real tool, which would just call the wrong thing with the wrong argument shape) — it's the model reaching for Gemini's own native code-execution capability instead of a direct function call, which doesn't exist here and can't be repaired after the fact. Mitigated in `src/lib/ai-site/prompt.ts`'s system prompt with an explicit instruction to always call tools directly with plain arguments and never via generated code/an interpreter. This is a prompt-level mitigation, not a structural fix — if it recurs with a specific model, that model may just not be reliable for this agent loop.

### Tools

Defined with `tool({ description, inputSchema: z.object(...), execute })` (`zod` v4), split across three files merged in `aiSiteTools()` (`src/lib/ai-site/tools.ts`):

| File | Tools | Does |
| --- | --- | --- |
| `src/lib/ai-site/tools.ts` | `listFiles`, `readFile` | Read the site from the tenant's `AiSiteFile` Prisma table |
| | `writeFiles`, `deleteFiles` | Change files; paths go through `normalizeProjectPath` (`src/lib/ai-site/paths.ts`), which rejects traversal, `node_modules`, `.next`, `.git`, `.vercel`, and `.env*` |
| | `runCommand` | Runs an allow-listed command (`npm`, `npx`, `node`, `ls`, `cat`, `grep`) in the Sandbox after syncing files; refuses `npm run dev/start` and any arg referencing `.env*` (see `references/security.md`) |
| | `cms_get_full_schema`, `cms_list_content_types`, `cms_get_content_type`, `cms_query_content`, `cms_list_components` | **Read-only** CMS introspection the *agent* uses while building — thin wrappers around `src/lib/cms-introspection.ts`, the same functions the external MCP server (`src/app/api/mcp/[[...transport]]/route.ts`) uses for its own `get_full_schema`/`list_content_types`/etc. tools. One source of truth; don't duplicate this logic a third time. The *generated site* never calls these — see `references/sdk-and-templates.md`. |
| `src/lib/ai-site/cms-tools.ts` (`cmsBuilderTools`) | `cms_list_field_types`, `cms_create_content_type`, `cms_update_content_type`, `cms_delete_content_type`, `cms_list_single_types`, `cms_get_single_type`, `cms_create_single_type`, `cms_update_single_type`, `cms_delete_single_type`, `cms_get_component`, `cms_create_component`, `cms_update_component`, `cms_delete_component`, `cms_list_webhooks`, `cms_create_webhook`, `cms_update_webhook`, `cms_delete_webhook` | **Write-capable** schema/webhook builder tools — call the exact same server actions the dashboard's own Content Types / Single Types / Components / Webhooks screens call (`src/actions/content-types.ts`, `single-types.ts`, `components.ts`, `webhooks.ts`). Zero duplicated validation/RBAC/plan-limit logic; those actions already call `getServerSession`/`getTenantAccess`/`checkPermission`/`enforcePlanLimit` themselves — see `references/security.md` for why that makes privilege escalation through the model structurally impossible. These always succeed now — the earlier "finalized schema" lock that blocked them is gone (see the `schema-architect` skill); the agent is expected to design/adjust the schema as it builds, not just read a pre-settled one. |
| `src/lib/ai-site/content-entry-tools.ts` (`contentEntryTools`) | `cms_create_content_entry`, `cms_get_content_entry`, `cms_update_content_entry`, `cms_delete_content_entry` | Real content **rows**, not schema — calls the exact same `src/lib/content/entry-service.ts` functions the dashboard's content editor and the MCP server's own `create_content_entry`/etc. tools call, extracted the same "one source of truth" way as `cms-introspection.ts`. Built as a `{kind: "staff", userId, role}` `ContentActor` from the real signed-in session (`access.userId`/`access.role`, threaded through `aiSiteTools()`'s context) — **never** `{kind: "system"}`, which would bypass the same workflow/plan-limit checks a human editor is held to. Exists specifically so the agent can seed realistic sample data into an already-finalized schema instead of the generated site showing empty collections. |

Tools return `{ error }` objects (or the action's native `{ error }` shape, passed straight through) instead of throwing for expected failures, so the model can react. The tenant's dedicated Prisma DB (when it has one) is the source of truth; never treat the sandbox filesystem as authoritative for anything except the generated site's own code.

**Zod schema gotcha (zod v4.4.3 + `ai`@7, this exact version combo):** a zod object schema passed as a tool's `inputSchema` with 4+ keys where any key uses `.optional()` breaks `tool()`'s overload resolution — TypeScript fails with `No overload matches this call` / `FlexibleSchema<never>`, with no runtime error to point at the cause. Use `.default(sentinelValue)` instead of `.optional()` everywhere in a tool's input schema (treat an empty string/empty array/`false` as "unset" in the handler) — confirmed fix, reproduced and isolated in `cms_query_content`'s schema while building this. Every schema in `tools.ts`/`cms-tools.ts` already follows this; keep it that way for any new tool.

**A second, unrelated zod→JSON-Schema gotcha: `z.record()` always emits `propertyNames`, even with a plain `z.string()` key and no checks.** Seen live as an `ai` SDK console warning ("JSON Schema propertyNames... OpenAI does not support...") whenever `openai/gpt-5-mini` was the active model. Traced to `cms-tools.ts`'s `fieldSchema.options`, defined as `z.record(z.string(), z.any())` — zod v4's own `toJSONSchema()` unconditionally adds `propertyNames` for *any* record, regardless of key constraints (confirmed by reading `zod/src/v4/core/json-schema-processors.ts`'s `recordProcessor`), and OpenAI's structured-output dialect doesn't support that keyword, so `@ai-sdk/openai` strips it with a warning before sending. The constraint is inconsequential either way (JSON object keys are always strings, so `propertyNames: {type: "string"}` enforces nothing a record doesn't already guarantee), so the fix was the schema, not the model: swap `z.record(z.string(), z.any())` for `z.looseObject({})` for the same "arbitrary extra keys" shape — it goes through `objectProcessor` instead of `recordProcessor` and never emits `propertyNames`, for any model. Don't reach for `z.record()` in a tool schema here; use `z.looseObject({})` for an open-ended key/value bag instead.

**"Update" tools are full replace, not partial patch — for schema tools specifically.** E.g. `cms_update_content_type` takes `name`/`description`/`showInCms`/`fields` all as *required* inputs (no optional/nullable), and the system prompt tells the model to call the matching `cms_get_*`/`cms_list_*` first and pass back the complete desired state. This was a deliberate choice to dodge the optional-field schema bug above entirely rather than work around it with `.nullable()` (untested whether that also triggers it) — don't reintroduce `.optional()` to make a schema update tool "more RESTful." `cms_update_content_entry` (content-entry-tools.ts) is the one deliberate exception: it merges `data` (empty object = no field change) because `updateContentEntry` in `entry-service.ts` is itself a merge operation by design, same as the dashboard's own content editor — don't "fix" it to match the schema tools' full-replace convention, they're different operations on purpose.

## In-process CMS tools vs. real MCP

AI Site does **not** connect to SaCMS's own MCP server as a client (no `@ai-sdk/mcp` `createMCPClient`, no bearer-token hop). Every CMS tool calls shared library functions or server actions directly, in-process, reusing the session auth `withStaffAuth` already resolved. This was a deliberate simplification over a reference app that *did* connect to an external MCP server per-project — don't reintroduce an MCP client connection for AI Site; extract-and-share (like `cms-introspection.ts` and the `src/actions/*` reuse above) instead, so there's one source of truth and no second auth hop.

Re-confirmed when the user explicitly asked "can AI Site talk to the MCP server" (expecting that would unlock capability the MCP server has but AI Site doesn't): the actual gap wasn't the connection mechanism, it was that AI Site's own tool set was missing content-entry CRUD and the MCP server's handlers for it were already correctly factored into `src/lib/content/entry-service.ts` — so extracting into `content-entry-tools.ts` (same pattern as `cms-introspection.ts`) closed the real gap without adding a client connection, same architectural answer as before. Before reaching for a real MCP client connection for *any* future AI Site gap, check first whether the MCP tool in question already calls a shared, extractable function — it almost always does, since the MCP route itself was built to reuse the dashboard's own actions/services wherever possible.
