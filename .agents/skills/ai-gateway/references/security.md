# AI Site security: verified findings and mandatory rules

This is a real audit against the current source, not a restatement of intent. Findings are labeled the same way a report back to the user would be: **VERIFIED** (checked against source and, where noted, a live call), **FIXED** (a real gap, now closed), or **NOT TESTED** (architecturally sound on inspection, not exercised live).

## FIXED this session

- **`runCommand` could read `.env.local` and leak the real `SACMS_API_KEY`.** `writeFiles`/`readFile`/`deleteFiles` all go through `normalizeProjectPath` (`src/lib/ai-site/paths.ts`), which blocks `.env*`. `runCommand` had no equivalent check at all — `cat .env.local`, `grep KEY .env.local`, or `node -e "require('fs').readFileSync('.env.local')"` would hand the real secret back as a tool result, which then sits in the model's context and could be echoed into chat or even written into a generated (tracked) file on a later `writeFiles` call. Fixed in `src/lib/ai-site/tools.ts`'s `runCommand` tool: every arg is checked against `/\.env(\.|$)/i` before the command runs, for every allowed command, not just the file-reading ones — this also catches the `node -e` vector, since the blocked pattern is matched against the literal script-string argument too. This is a denylist, not a sandbox — a sufficiently obfuscated attempt (e.g. building the string `.env.local` character-by-character inside a script) could still slip past; that residual risk is accepted the same way `normalizeProjectPath`'s denylist already accepts it elsewhere in this codebase.
- **No rate limit on the preview endpoint.** Unlike the chat route (gated by `AI_SITE_TURN_COST`), `POST .../projects/[projectId]/preview` had zero cost and zero rate limit — a tight client loop (or a bug in `PreviewPane`) could hammer real Vercel Sandbox provisioning with no economic or request-count friction at all. The MCP server's `deploy_to_sacms` tool already has a dedicated cooldown for the identical reason ("each deploy triggers a real Vercel build"). Added the same pattern: `rateLimit(`ai_site_preview:${tenantId}`, { limit: 20, windowSeconds: 60 })` in the preview route.
- **`lib/sacms.ts` (the generated site's SDK wrapper) had no `server-only` guard.** `SACMS_API_KEY` isn't `NEXT_PUBLIC_`-prefixed, so Next.js's bundler already resolves it to `undefined` in client bundles rather than inlining the real value — but that's a silent failure mode (broken fetch, not an obvious build error) if the agent or a later human edit ever imports `@/lib/sacms` from a Client Component. Added `import 'server-only'` to the template (`src/lib/ai-site/template.ts`) and `server-only` as a real dependency, so the mistake fails loudly at build time instead of quietly at runtime.

## VERIFIED safe (checked against source, no change needed)

- **Tenant isolation / IDOR.** Every `AiSiteProject`/`AiSiteChat` lookup across all 6 API routes scopes by `tenantId: access.tenantId` (or, for the one `findUnique`-by-id lookup in the messages route, an explicit `chat.project.tenantId !== access.tenantId` check immediately after) — confirmed by direct grep across every route handler, not assumed from one example.
- **CMS mutation tools (`cmsBuilderTools`, `src/lib/ai-site/cms-tools.ts`) cannot exceed what the human user could already do.** Each tool calls a dashboard-facing server action (`src/actions/{content-types,single-types,components,webhooks}.ts`) that independently re-derives `getServerSession`/`getTenantAccess`/`checkPermission`/`enforcePlanLimit` from the ambient request — not from anything the model asserts. A prompt-injected instruction telling the model to "delete all content types" can make the model *call* the tool, but the action underneath still enforces the real human session's actual RBAC role and plan limits; it cannot escalate privilege beyond what that human already has in the dashboard.
- **Webhook delivery (the outbound POST when an event fires) is SSRF-protected.** `src/lib/webhooks.ts` routes every delivery through `safeFetch`, at all four call sites (confirmed by grep) — a webhook URL the model is asked to create via `cms_create_webhook` can't be used to reach internal/metadata-service addresses at delivery time. (Webhook *creation* itself takes an arbitrary URL with only `z.string().url()` validation — that's intentional; the SSRF guard belongs at the point data actually leaves the server, which is delivery, not creation.)
- **Path traversal on file tools.** `normalizeProjectPath` rejects `..`, absolute paths, `node_modules`, `.next`, `.git`, `.vercel`, and `.env*` — exercised by `writeFiles`, `readFile`, `deleteFiles`. (`runCommand` is the separate surface fixed above — it never went through this function at all.)
- **Secrets never reach `AiSiteFile`/the Code tab.** `writeFrontendEnv()` (`src/lib/ai-site/sandbox.ts`) writes `.env.local` via `sandbox.writeFiles([...])` directly against the Vercel Sandbox filesystem — never through `writeProjectFiles`/Prisma, so it's structurally impossible for the Code tab (which reads `AiSiteFile` rows) to ever display it, independent of the `runCommand` fix above.

## NOT TESTED (sound on inspection; needs a live run to be sure)

- **`getServerSession` resolving correctly from inside a `tool.execute()` callback.** `src/actions/*.ts`'s session lookup relies on `next/headers`'s request-scoped `AsyncLocalStorage`, which should propagate through `streamText`'s internal async step loop since nothing in that chain crosses a new HTTP boundary — but this has not been exercised with a real request. If a `cms_create_content_type` call ever returns `{ error: "Unauthorized" }` when the human is clearly logged in, this is the first thing to check.
- **Full tool-calling agent loop against live Vercel Sandbox + AI Gateway credentials** — project creation → chat → tool calls → file writes → live preview → credit deduction/refund. Individual pieces were verified in isolation this session (a real Gateway call, the repair-tool-call fuzzy match, the frontend-env injection code path reviewed but not run against a live Sandbox) — not the full chain together.

## Mandatory rules going forward

1. **Any new `runCommand`-like capability (or a new allowed command) must pass through the same `.env` check**, not a fresh one bolted on separately — if the check ever moves, move the one check, don't add a second.
2. **Any new tool that can write arbitrary file content must go through `normalizeProjectPath`** — never accept a raw path from the model without it.
3. **Any new endpoint that can trigger real external spend (Sandbox provisioning, a Gateway call, a deploy) needs either a credit cost or a `rateLimit` cooldown, not neither.** The chat route has the former; the preview route now has the latter; a future endpoint needs one of the two, consciously chosen, not accidentally skipped.
4. **Never let a CMS mutation tool derive its authorization from anything the model says.** The model's job is to decide *to* call a tool; the server action's job is to decide whether that call is *allowed*, from the real session — keep that split intact for any new write-capable tool.
5. **A secret that's auto-provisioned and auto-injected (API tokens, the Gateway key) must never be written to a path the model's own tools can read back** — `AiSiteFile`/Prisma, not the raw Sandbox filesystem, is what `readFile`/`listFiles` expose; keep the secret on the other side of that line.
